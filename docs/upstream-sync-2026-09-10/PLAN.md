## 3. 集成策略

### 3.1 先分批实现，再真实合并历史

在独立集成分支上按功能引入、适配并验证。仅对边界清楚且依赖已满足的提交使用 cherry-pick -x；复杂提交按功能移植并在提交说明中记录完整上游 SHA、保护能力 ID 与阶段 ID。

每个阶段可拆为多个独立单元，通常每单元 1–3 个提交或一个不可分的接口变更。阶段包含十余个提交并不意味着一次全部操作。开始单元前逐个核查父提交差异、调用方、DTO、数据库和前端依赖。batches.json 的依赖是执行门槛，不声称它已经穷尽所有编译或业务依赖；新增依赖先写入台账，检查无环后继续。

完成分批集成后，在 B17 对固定上游目标执行真正的 merge --no-ff --no-commit，审查剩余差异和自动合并结果，解决冲突后创建双亲合并提交。这一步可能再次产生冲突，需按台账重新核对；不能只检查“有冲突”的文件，自动合并的文件也可能产生行为回退。

禁止用 merge -s ours、全文件一律取 ours/theirs、删除本地下游测试、关闭失败断言或跳过账务检查来制造“合并成功”。最终向下游 main 合并不能使用会丢失上游祖先关系的 squash 或重新挑拣替代。

### 3.2 准备与隔离

B00 先核对当前分支、3 个未推送提交和未跟踪 output/计划文件；保存基线 Git bundle、计划副本与清单。bundle 只保存 Git 对象，不包含未跟踪文件，因此这两类备份必须分别完成并核对可读性。

创建基线保护引用及独立工作树，名称若已存在必须核对其目标后复用。不要删除现有工作树，不执行 reset --hard 或 clean 来清理用户改动。创建工作树后先转移并提交计划文件，再安装工作树自己的依赖；不能共享可写 node_modules 或依赖原临时目录。

本计划编写阶段不创建工作树、不执行 cherry-pick、不改数据库。执行阶段的准备命令及恢复限制见 RESUME.md。

### 3.3 冲突处理顺序

先确定不变的行为契约，再合并类型与接口、服务逻辑、控制器与路由、前端消费方、测试和翻译。每个冲突记录“上游意图、本地能力、最终实现、验证方式”；纯文本消除冲突不算验收。

保留项目分层、common JSON 包装、三库兼容、GORM 锁助手、可选标量指针语义和计费饱和审计。修改计费表达式前读 pkg/billingexpr/expr.md；编辑前端文案或 locale 前加载 i18n-translate，并遵守 web/AGENTS.md。项目名称、署名与许可信息不得被移除。

## 5. 三项必须先解决的兼容性设计

### 5.1 渠道编号与任务插件

下游 61/62/63/64 分别是 Codex、Claude Code、CodeBuddy、Vercel。不得改变它们在现存数据库、API、配置、前端选项中的含义。

B14 前盘点完整渠道枚举、编号索引数组、分发表、前端映射和存量数据后再确定 TaskPlugin 的空闲编号，并记入 DECISIONS.md；计划不猜测新编号。兼容导入必须携带来源和明确类型映射，不能把所有“61”统一迁移为插件。

上游移除或替换内置任务适配器时，要保留旧任务查询/轮询/取消/结算入口，或先完成可审计迁移。运行中任务不得丢失、重复扣款或重复退款。视频价格需建立旧配置到新配置的对应关系，不能以清空价格要求用户重配作为“保留完成”。新插件默认启用与升级策略需兼顾已有部署，实验性标记如实保留。

### 5.2 钱包、额度及存量数据

先保存 schema、行数、关键额度总和与抽样账单，分别在脱敏数据库副本演练迁移。确认实际列类型、索引、事务和锁；不能绕过启动检查代替升级。

钱包上限扩展与单请求计费上限分离。保留 QuotaFromFloat/QuotaRound/QuotaFromDecimal 的 checked 路径与饱和审计、输入上限、AddOtherRatio 校验，以及预扣、结算和退款的完整安全链。

一旦余额超过旧字段可表示范围，不允许直接降级旧二进制或缩回列类型。回退优先回到兼容新 schema 的上一稳定二进制；恢复迁移前备份必须停止写入并明确处理迁移后的交易，不能静默抹掉新增账务。

### 5.3 安全中心与下游定制

保留现有账户 ID、Passkey 凭据与名称、注册邀请码次数、OAuth 绑定与头像、自助资料、登录代理、用户 RPM 和封禁语义。安全中心升级覆盖旧会话、重新验证、解绑、删号、令牌轮换和管理员操作。

日志改为 public/admin/root/audit 投影时，把下游原始请求与完整请求体诊断放入适当权限域。逐角色验证读取、导出和详情接口；“隐藏 UI”不能替代后端权限。自动封禁、上游拦截和诊断记录仍须协同工作。

## 7. 持久检查点与中断恢复

每个不可分操作采用“先写意图，再改代码，后写结果”：

1. 在 state.json 和 CHECKPOINTS.md 写入阶段、单元、基线 HEAD、活动操作、目标 SHA、下一步和需要保留的未提交文件。
2. 每次只执行该单元。Git cherry-pick/merge 状态、冲突列表和未跟踪新文件均记录；完成冲突文件后及时保存文件。
3. 得到可编译实现后提交代码，记录代码提交 SHA；在该提交上运行验证，输出立即保存到 evidence/runs，不只留在终端。
4. 验证通过后更新相关上下游记录和保护项，提交台账；代码提交与台账提交可以分开，避免把提交自己的 SHA 写入自己造成循环。
5. last_verified_code_commit 只指向实际验证过的代码提交。其后若只有计划文件变动，验证仍可引用该代码提交；业务代码再变必须重新验证。
6. 台账先写同目录临时文件，确认 JSON 可解析，再原子替换并保留前一版本。发现临时文件或损坏 JSON 时按 RESUME.md 核对，不自动覆盖 Git 状态。

发生硬中断时，已保存的源文件和 Git 操作仍可恢复；尚未完成的测试没有退出码就视为未完成。未提交且未保存的编辑无法承诺恢复，因此每个文件编辑和每个操作意图都及时落盘。不要等一个大阶段全部结束才写检查点。

## 8. 回退与交付

普通代码批次以独立提交回退，保留后续依赖关系，通常使用 revert 并跑相关回归。若要取消活动 merge/cherry-pick，先保存 staged/unstaged 补丁、未跟踪新文件和操作说明，再决定 abort；不默认丢弃半成品。

数据变更遵守各批迁移方案；代码 revert 不等于数据回退。备份需校验可恢复，不能只确认“文件存在”。

B19 先同步下游 main 的最新状态并复核集成差异；最终 PR/合并目标始终是 MAakber/new-api。PR 使用仓库模板、核对当前 Git 身份与历史核心作者，按规定披露 AI 协助；人工确认项不代替用户勾选。对新增加且尚未授权的外部发布操作，先完成可审查结果再处理授权。

交付包括最终合并 SHA、固定上游 SHA、120/153 项闭环清单、最终测试与迁移报告、必要运维变更、回退边界和未解决项列表。未解决项必须为空才可宣告本计划的完整合并目标完成。
