# 钱包 BIGINT 迁移与兼容回退

本文是待发布版本的操作说明。当前只在本地隔离数据库演练；生产没有执行迁移或部署。生产版本为 MariaDB 11.4.4。脱敏生产副本演练仍是最终发布前的待办。

## 数据约定

`users.quota`、`users.used_quota`、`users.aff_quota`、`users.aff_history` 使用有符号 BIGINT。钱包对外整数范围是 `-(2^53-1)` 至 `2^53-1`；充值、兑换额度须为正数。单请求扣费仍受 int32 饱和、输入上限与管理员审计保护。日志中的单笔消费列不因钱包升级而放宽。

SQLite 的 INTEGER 存储已支持 64 位有符号整数，不执行 ALTER。MySQL/MariaDB 和 PostgreSQL 存量 INT 列须显式升级；普通启动及非主节点启动都会先拒绝旧列、缺列或无符号列。不能用 `SKIP_64BIT_QUOTA_SCHEMA_CHECK` 代替迁移验收。

原始基线程序在本次三种外部引擎上的新建库均已生成 BIGINT；不能从 Go `int` 字段或 `type:int` 标签推断实际列宽。必须读取生产副本的真实元数据；已经满足有符号 BIGINT 的四列无需再 ALTER。测试分别覆盖这一情况与真正的旧 INT 存量库。

2026-09-11 15:17 UTC 已对当前生产进行只读元数据检查：上述四列实际均为有符号 `bigint(20)`、可空、默认 0；在该状态下无需执行本说明的额外扩列 SQL。该检查没有修改数据库，也没有替代生产副本迁移及回退演练。详见 `evidence/B18-production-readonly-preflight.json`；生产状态变化后应按实际元数据判断。

## 执行前

1. 在独立副本完成本说明对应演练，核对所用程序和 SQL 的 SHA256。准备主库、独立日志库及配置的可恢复备份，验证恢复方法。不得把凭据或真实请求写入 Git。
2. 停止所有节点接收新请求，排空流式请求、在途扣费、支付回调处理与批量写入；停止任务轮询及后台余额写入。确认所有写入方已停止后，记录最终备份位置与交易截止点。
3. 保存实际表定义、索引、用户行数、四列的精确 SUM/MIN/MAX/NULL 数量、相关充值/兑换/订阅/日志行数与最近交易标识。使用数据库的精确整数/DECIMAL 输出，避免经过 JavaScript 浮点累加。
4. 核对四列均存在。所附 MySQL SQL 适用于项目原始的可空、默认 0 列；若实际列有额外约束、注释或特殊默认值，先生成保留这些属性的等价 ALTER 并在副本验证。缺列必须核对历史 schema，不能猜测金额或补零后继续。

## 显式升级

- MySQL 5.7 / MariaDB 11.4：执行仓库 `model/migrations/wallet64_mysql.sql`，一次 ALTER 扩展四列。MySQL DDL 隐式提交，不以事务回滚承诺恢复。
- PostgreSQL 9.6：执行 `model/migrations/wallet64_postgres.sql`。可在显式事务内执行并核对后提交；预留表锁和重写所需时间与磁盘空间。
- SQLite：保留原文件和完整 WAL 备份，直接由候选程序验证。

重新读取实际列定义与上述统计，要求金额、NULL 数量和行数逐项相等。已完成部分列时，仍保持停写，核对实际 schema 后重跑完整扩展 SQL；两份 SQL 可重复执行，不缩小列也不修改余额。缺列或不符合预期的数据必须先解决，不能继续启动。

启动候选程序，确认不再报告旧钱包列；连续重启两次，确认没有再次 ALTER 或把 BIGINT 缩回 INT。检查账户、会话、多个具名 Passkey、注册码消耗、61–64 渠道编号、自定义余额配置和历史任务。随后只用隔离账户验证充值、负余额调额、预扣/结算/退款、兑换码和操作日志的精确金额。生产验证与恢复接流量须在单独的发布步骤进行。

## 回退边界

不能未经验证就把原始 `403f7d9d` 二进制作为回退程序：它没有本轮的钱包范围保护及新密码格式读取能力。回退须使用经过演练的兼容版本，保留 BIGINT，禁止缩列或静默恢复旧余额。

本批选定 `a335f0dd55f00ac0bc89a830f62617247551accc` 作为钱包兼容回退源码。它包含 BIGINT 声明、钱包范围检查、B10 订阅事务修复、双密码格式读取和下游功能；其前端与后端须成套构建。构建产物、哈希和演练结果写入 B11 证据清单。它是本批的兼容恢复点，不自动适用于后续插件/配置迁移；B18 必须重新确认最终候选的回退方案。

演练顺序：候选写入超过 int32 的正/负余额和交易 → 兼容回退程序启动两次并核对数据 → 通过旧兼容业务接口新增一笔充值 → 切回候选核对两批交易均保留。不会运行原始基线来尝试缩列。

如果必须恢复迁移前备份，继续停写，先导出并核对截止点之后的全部账务变化，制定逐笔补录或冲正方案；没有交易对账就不能恢复接流量。数据库 schema 迁移失败时依据实际列和备份恢复，Git 回退不能恢复数据库。
